# Stock execution and automation

The current chain 46630 deployment has two immutable strategy routes, TSLA and AMZN. Its `AlphaForgeStrategyTestStock` tokens and `AlphaForgeStockReserve` settle AF-USDC against separately funded token inventory. They do not provide real TSLA/AMZN shareholder rights, brokerage custody, or mainnet settlement. Replacing UI copy cannot change that contract property. Real equities need an approved tokenized-share/custody provider or brokerage integration, suitable asset and venue contracts, funded reserves, and a newly verified deployment manifest. The fixed `Strategy[2]` factory cannot register creator-published custom IDs.

The worker now implements the current StrategyVault ABI end to end: source-confirmed feed updates, owner-signed policy admission, bounded execution, restricted encrypted-keystore signing, single-attempt transmission, and canonical receipt reconciliation. `--prepare` performs one planning tick; `--watch` continuously prepares without decrypting keys or submitting. Neither command places brokerage orders. Only `--activate PRIVATE_CONFIG.json PRIVATE_ACTIVATION.json` with `AF_STOCK_EXECUTION_ACK=I_AUTHORIZE_STOCK_WORKER_46630` enables the separately reviewed signing path. CI cannot activate it.

The provider integration reads authenticated Alpaca clock/calendar and IEX quote endpoints using GET. It preserves holidays, early close and New York DST from the provider. IEX is a single-exchange reference, not consolidated SIP/NBBO. A closed session produces only a real calendar update; no substitute price is generated. EMA uses consecutive same-session raw minute bars, waits 90 seconds from each bar start for late-trade revisions, requires three slow periods of warmup, and rejects missing, unfinished or stale bars. These rules follow Alpaca's [market-data coverage](https://docs.alpaca.markets/us/docs/market-data-faq) and [minute-bar update behavior](https://docs.alpaca.markets/us/docs/real-time-stock-pricing-data). A data entitlement failure pauses the worker; there is no fallback to display-only Nasdaq data.

Owner consent is an EIP-191 wallet message generated by `stockConsentMessage`. It binds chain, manifest digest, owner, Vault, target strategy, initial execution version, exact current grant, policy, expiry, position cap, price exit thresholds and a unique nonce. Creator publication grants no trading authority. Supported policies are BUY_AND_HOLD (bounded investment of available cash), DCA (one installment after the last confirmed buy plus the interval, without catch-up purchases), and EMA_CROSS (completed-bar crossover). Stop/take price thresholds trigger an order-limited exit and latch after the first confirmed exit; the policy does not reenter. The owner may pause the private registry independently of publication, revoke the onchain grant, or remove the signed registry entry.

Every order is checked against factory membership, pinned contract hashes, canonical chain state, the regular session, price/calendar age, stock reserve inventory, tracked and actual Vault balances, maximum position, owner validity, grant maximum order/lifetime buy/slippage, gas funds and the worker's total gas budget. BUY_AND_HOLD can invest additional cash only within these limits. A worker-managed session expects the initial execution version plus its own confirmed executions. Owner manual trading, reconfiguration, revocation or any unexplained version change pauses it and requires fresh consent; an identical regrant cannot revive an old session.

`OrderJournal` reserves a nonce before signing, persists the exact signed envelope before transmission, and marks the outcome uncertain before the single send. A lost RPC response, failed signer, crash, changed authorization after signing, or noncanonical receipt blocks that signer. Reserved/signed envelopes are never automatically retried or freed. Reconciliation requires three canonical confirmations, exact sender/target/input/value/nonce, matching emitted feed values or `StrategyExecuted` input/output/version, and a second canonical block check. A reorganization pauses reuse. Only unsigned stale drafts may be cancelled. Separate hash-checked source/decision storage preserves provider responses and strategy evidence; ledger databases are never restored or edited by the worker.

Private operational status exported to `status.json` contains mode, operational reason, tick time, strategy, pending hash, manifest and executor bindings, and the registry path. The public HTTP status removes the registry path and pending hashes. It contains no wallet account identifiers, provider credentials, signed envelopes or source payloads. The authenticated application may provide a private `sessionProvider` and `sessionActive` callback; read failure pauses admission and owner pause is rechecked both before and after signing. The server should load this status file read-only and mark it unavailable if stale. Public readiness is distinct from the owner's private opt-in status.

Deployment prerequisites are a verified manifest containing feed/stock/reserve hashes, usable read RPC, private Alpaca IEX data credentials with clock/calendar access, exact onchain feed keeper/reference identity bindings, a funded keeper signer, a distinct funded executor named in each owner's onchain grant, and signed owner consents. Do not reuse native-conversion quote or claim voucher keys. The supplied example is deliberately inert (`feeds` and `signers` empty). Private config, credentials, registry, activation and keystore/password files must be regular nonlinked files owned by the worker UID with mode 0600; worker and host-wide nonce directories use 0700. Each signer has a host-wide ownership lock. A crash lock is retained for explicit canonical nonce reconciliation and recovery, never blindly removed by restart.

The activation file binds `configurationHash = stockEvidenceHash({config, manifest})`, `schemaVersion:1`, `chainId:46630`, `scope:"STOCK_REFERENCE_AND_USER_CONSENT_EXECUTION"` and a bounded Unix-second `validUntil`. A changed/expired/removed activation file pauses the worker, including before transmission. Keystore files must be version-3 AES-128-CTR/scrypt within the admitted work-factor bounds. External signer implementations can use the same `RestrictedSigner` interface without passing keys into the CLI. Production activation remains a concrete separate operator decision; installing this source or publishing creator research alone cannot activate trading.

The product API exposes actual contract readiness at `GET /api/launch-market/automation/status` and wallet-private authorizations at `GET /api/launch-market/automation/sessions`. Owner `POST /automation/start` uses the canonical wallet consent plus the expected registry revision; `POST /automation/pause` uses its digest plus the expected revision. These paths use the same selected wallet identity, exact origin and per-device CSRF as funding and community actions. Pause remains available when the worker is stopped or the new-session storage quota is full, and writes the worker's active list atomically. A pause prevents future admission; an already-broadcast transaction requires canonical reconciliation or owner onchain revocation.

The web server defaults to execution unavailable. Operators may configure `AF_STOCK_STATUS_FILE` and the public-role `AF_STOCK_EXECUTOR_ADDRESS` only after worker activation. The bounded private status must be owned by the server UID, mode 0600, and bind the current `manifestDigest`, the activated `executorAddresses`, and the exact `sessionsFile` path at `<AF_COMMUNITY_DATA_DIR>/stock-owner-consents.json` (the default directory is `<AF_MARKET_DATA_DIR>-community`). Both processes must be able to read this private atomic registry under the same service UID. Availability requires ACTIVE/RUNNING status no older than 20 seconds plus the selected strategy's fresh chain/feed/calendar/reserve readiness. The public response excludes registry paths, owner session details and pending transaction hashes. Every Start rechecks current factory registration, owner, grant, execution version, expiry and operator state before persisting consent; it never signs or broadcasts a transaction in the web process.
